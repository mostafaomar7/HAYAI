## 1. Deleting an internal device that has orders answers 500

`DELETE /admin/external-devices/{id}` (the dashboard's **Internal Medical
Devices → Devices** screen) answers:

```json
HTTP 500
{"success": false, "message": "Server error. Please try again later."}
```

for every device that has orders. From your own audit log:

| When (UTC) | Request | Status |
|---|---|---|
| 2026-10-22 18:50:11 | `DELETE /admin/external-devices/3` | 500 |
| 2026-10-22 18:50:17 | `DELETE /admin/external-devices/4` | 500 |
| 2026-10-22 18:50:25 | `DELETE /admin/external-devices/4` | 500 |
| 2026-10-22 18:50:29 | `DELETE /admin/external-devices/2` | 500 |
| 2026-10-22 18:55:36 | `DELETE /admin/external-devices/4` | 500 |
| 2026-10-23 14:57:08 | `DELETE /admin/external-devices/4` | 500 |

`GET /admin/external-device-orders` shows device 2 with 1 order, device 3
with 7, device 4 with 3, which matches every failure above. Most likely the
orders table's foreign key refuses the delete and the exception is not
caught.

For comparison, the group-order module already does this right:
`DELETE /admin/external-devices/devices/9` answered **409** the same day.

**What we need:**

1. A device with orders answers **409**, not 500, with a readable message,
   in the same shape as your other refusals:

   ```json
   HTTP 409
   { "success": false,
     "message": "This device has orders and cannot be deleted.",
     "error_code": "DEVICE_HAS_ORDERS",
     "orders_count": 7 }
   ```

   Please don't cascade the delete: those orders are purchase history.

2. Confirm the way to take such a device off the store instead. Is it
   `PUT /admin/external-devices/{id}` with `is_available: false`? Does that
   hide it from the apps, or only mark it out of stock? If neither, we need
   a field that does.

3. Any other uncaught 500s on this module's write routes (`PUT`/`POST`
   update) for a device with orders, if you can check.

**Dashboard side, done:** a 409 now shows "This device already has orders,
so it can't be deleted" (EN/AR); any other failure shows your `message`
instead of a generic "try again". It reaches the server with the next
deploy. Once you answer item 2, we'll add a "Hide from store" action next to
Delete.

## 2. Patients registered with only a name and an email

On **Users → Patients**, some rows have no phone, governorate or gender. The
dashboard is not dropping them: `GET /admin/patients` returns `null` for all
three.

Of the 25 patients today, **8** are like this: ids 129, 119, 118, 95, 94, 33,
31 (and 34/111 have a phone but no governorate). All of the empty ones have
a Gmail address and nothing else, which looks like **Google sign-in**: Google
gives a name and an email, and the profile fields are never asked for
afterwards. Example, `GET /admin/patients/129`:

```json
{ "id": 129, "name": "Cesar Bates", "email": "cesarbates.06239@gmail.com",
  "phone": null, "governate": null, "nationality": null, "gender": null,
  "residence": "inside_egypt", "created_at": "2026-10-22T13:50:59+00:00" }
```

**Questions:**

1. Is this the Google (or Apple) sign-in path? Can the list carry the sign-up
   method (`registration_method: "google" | "apple" | "email" | "phone"`) and
   `profile_complete`, so the dashboard can mark these rows as "Profile not
   completed" instead of showing blanks?
2. Does the app ask these users to complete their profile after social
   sign-in? If not, that's an app change (phone, governorate, gender
   required before first use), and the reason the data is missing.
3. The list's key is `governate`, not `governorate`. Fine as is, but
   confirm it will not be renamed, since the dashboard reads that key.

**Also noticed:** every patient without a plan exception is on plan 64,
named **"QA Patient Plan (internal)"**, with four modules. If that is the
real default patient plan, its name should change; if it is a QA plan, new
patients should not be getting it.
